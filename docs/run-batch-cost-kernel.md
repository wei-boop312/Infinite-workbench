## 当前状态流

```text
创建批次
  → awaiting_confirmation
  → 服务端核对成本快照、批次上限、项目预算和确认权限
  → 冻结预算
  → queued
  → 为每个预期输出创建独立 RunJob
  → 执行器领取限时租约（leased）
  → 凭当前租约启动（running）
  → succeeded / partial / failed / billing_unknown
```

`awaiting_confirmation` 和尚未启动的 `queued`/`leased` 批次可以取消。已经启动的 `running` 批次不能直接释放预算；计费未知时同样禁止取消或重试，必须先完成外部账单核对。

## 关键约束

- 创建请求必须带用户动作级 `idempotencyKey`；同一租户、项目和幂等键只对应一个参数快照。
- 重复请求参数一致时返回原批次；参数发生漂移时返回冲突，不创建第二个批次。
- 每个输出任务有独立幂等键，不能用一个供应商请求冒充整个批次。
- 预计成本由服务端假定价器计算，客户端只提交可接受的最大成本。
- 确认请求必须回传用户看到的预计金额和币种；不一致时拒绝，避免确认过时页面。
- 只有拥有 `run:confirm` 权限的成员才能冻结预算。
- 服务端同时检查批次成本上限和项目可用预算；界面提示不能替代服务端拒绝。
- 成本账本采用追加记录：估算、预留和释放不会覆盖旧记录。
- 审计记录采用追加事件，保留创建、确认失败、确认成功、预算冻结、任务创建、取消和预算释放。
- 调度器按配置的最大领取数量、项目并发和供应商并发只领取一部分排队任务；剩余任务保持 `queued`，不会一次性冲击供应商。
- 每次领取生成独立租约编号、逻辑执行器身份和到期时间；启动任务必须同时匹配当前租约与执行器身份。
- 供应商时间窗口限制通过持久化的 `job-leased` 审计计算，任务结束释放并发槽位，但不会绕过窗口启动次数。
- 未启动的过期租约可以回到队列；已启动任务的租约过期会进入 `billing_unknown`，不会被另一个执行器直接重跑。
- 慢任务只有在人工或定时对账时才转为 `timed_out`，不会自动创建重试任务。
- 失败或超时任务只能人工重试；新任务记录 `retryOf`、递增尝试次数和新的幂等键，并重新冻结单任务预算。
- 已成功的输出在部分失败时继续保留，不因其他输出失败而回滚。

## 持久化与重启恢复

- 任务内核接受可替换的状态存储接口；保留内存及单进程 JSON 原型，本地工作台使用 SQLite 事务适配器。在写锁下重新加载、验证并一次性提交聚合，预算、租约、任务和财务记录不会被其他进程的旧缓存覆盖。
- 快照合同带固定 `schemaVersion`，包含项目预算、批次聚合、逐任务预留、假执行场景和创建请求指纹；供应商密钥不进入快照。
- 文件存储先写同目录临时文件，再原子替换正式快照，避免正常中断留下半个 JSON 文档。
- 恢复时重新构建幂等索引，并核对预算配置、任务归属、预留金额、实际成本和项目总账；快照损坏或金额不守恒时启动失败，不会把预算重置为零。
- `queued` 任务在重启后保持排队，可以继续由调度器领取。
- 未到期且尚未启动的 `leased` 任务跨重启保持独占；到期后才会以新租约重新领取。
- 进程中断前处于 `running` 的任务，其外部执行和扣费结果无法从本地确定，因此恢复为 `billing_unknown`，追加恢复审计和未知账本，继续冻结原预留。
- 恢复过程不会自动创建重试。只有后续核账明确外部结果后，才能决定结算、释放或允许人工重试。

## 当前假定价与成本

- 当前适配器固定为 `mock-product-retouch-v1`。
- 默认每个预期输出估价 25 个最小货币单位；测试可以注入其他单价。
- 假调度器可模拟成功、明确失败、部分失败、慢响应和计费未知。
- 成功任务按假实际单价结算，估价与实际成本的差额立即释放；失败或超时任务释放全部单任务预留。
- 计费未知任务继续占用预留，且禁止重试，避免潜在重复扣费。
- 估价、结算和预算预留只是验证记账逻辑，不代表真实扣费。
- 当前任务内核不进行任何模型、MCP 或外部网络请求。

## 计费待核对人工解决

- 只有拥有 `run:reconcile-billing` 独立权限的核账人员可以处理 `billing_unknown`；普通执行和重试权限不能替代核账权限。
- 请求必须携带唯一 `resolutionId`、核账人所见预留金额、币种和外部 `evidenceRef`，避免根据过时页面或口头判断释放预算。
- `charged` 表示外部证据确认已扣费：核账人填写实际最小货币单位，系统结算实际金额并释放预留差额。
- `not-charged` 表示外部证据确认未扣费：系统把实际金额记为 0 并释放全部预留。
- 同一核账动作编号和相同参数可以安全重复提交；同编号参数漂移会冲突，已经解决的任务不能用另一个动作覆盖结论。
- 实际扣费超过当前预留时系统拒绝自动入账并继续保持 `billing_unknown`，需要进入更高等级的超额处理流程。
- 超额处理现已支持申请、独立审批、批准结算与拒绝保留冻结；完整规则与边界见 `billing-overage-approval.md`。待审批申请不能被普通核账绕过，审批也不能提高项目预算。
- 核账完成后原任务转为带明确失败原因的 `failed`，保留核账人、时间、证据引用和动作编号；如仍需产出，必须再由人工创建新重试。
- 原 `unknown` 账本和审计不删除，系统追加 `settled` 或 `released` 账本以及核账审计，形成完整证据链。

## 当前 API

- `POST /v1/run-batches`：创建待确认批次。
- `GET /v1/run-batches/:id`：读取完整批次、任务、账本和审计。
- `GET /v1/projects/:id/run-batches`：按租户和项目读取历史批次列表，要求 `run:read` 权限。
- `POST /v1/run-batches/:id/confirm`：核对快照并冻结预算。
- `POST /v1/run-batches/:id/dispatch`：按并发上限执行一批排队假任务。
- `POST /v1/run-batches/:id/claims`：按项目、供应商和时间窗口限制领取任务租约。
- `POST /v1/run-jobs/:id/execute`：核验执行器身份和租约编号后启动一个假任务。
- `POST /v1/run-batches/:id/reconcile`：检查慢任务是否超时，不自动重试。
- `POST /v1/run-batches/:id/cancel`：取消批次并释放尚未消耗的预留。
- `POST /v1/run-jobs/:id/retry`：人工确认单任务重试成本并创建关联的新尝试。
- `POST /v1/run-jobs/:id/resolve-billing`：凭外部证据确认已扣费或未扣费，并结算或释放预留。
- `POST /v1/run-jobs/:id/billing-overages`：提交超预留扣费升级申请。
- `POST /v1/run-jobs/:id/billing-overages/:overageId/review`：由独立审批人批准或拒绝申请。
- `GET /v1/projects/:id/budget`：读取项目预算占用。

默认启动不注入任务内核，上述接口返回 `run_kernel_not_configured`。注入任务内核但不配置状态存储时仍为纯内存模式；`FileRunKernelStateStore` 只支持单进程原型。`SqliteRunKernel` 与 `SqliteRunKernelStateStore` 支持同一本地磁盘上的多进程原子操作，恢复用执行租约期限判断，不将其他服务的运行任务视为自身重启残留。生产 PostgreSQL、规范化表结构与异步执行器尚未接入；参见 `local-database-transactions.md`。

## 画布面板与本地桥接

- “任务与预算”按项目显示可用模拟预算、预留和已结算金额；查看预估不等于确认付费。
- 输入绑定原图资产和不可变约束快照；服务端本地目录检查归属、商品锁定、图片输出及蒙版底图。`validateInputs` 在创建、确认、领取、启动和重试时执行；实际原文件必须通过魔数、完整解码、尺寸和 SHA-256 校验并留存本机数据库，任务操作内重新核对保存的原文件，失败不新增预留或外部请求。
- `POST /studio-api/context` 仅是开发环境资产元数据登记，不上传原始二进制，不是生产资产权限服务。项目预算动态登记只能由本地适配器调用，不能由浏览器指定额度。
- 浏览器只请求同源 `/studio-api/`；Vite 中间件检查回环 Host、Origin 与自定义标记后，使用服务端私有身份调用任务 API。设计师身份不具备超额审批权限，明确的审批路由使用只具备读与审批权限的模拟审批人；此模式不是多人鉴权方案。
- 本地目录追加保存不可变上下文，与 SQLite 事务任务状态及图片原文件配合恢复预估、记录和预算；待确认且没有任务的批次在重启后仍保持待确认。
- 创建响应丢失时，客户端保留动作编号，重复创建复用原批次。核账响应不确定时，当前面板保留动作编号及提交参数，避免反复修改后重复入账。
- 运行中的任务定时核对状态；不会自动派发新的排队任务，也不会自动重试失败任务。
- 成功的模拟记录可回到画布；稳定的节点编号防止重复放置，并支持画布撤销/重做。任务编号、批次编号和冻结约束来源经自动保存保留，但没有真实媒体产物。
- 项目包携带画布中的来源标记，不包含服务端预算、账本和任务历史；导入副本不会复用或获得原项目的执行权限。
- 任务与预算 API 绕过 Service Worker 缓存，断线时明确报错；不能把历史缓存当作当前可支配金额。
- 前端任务面板懒加载，首屏不加载完整任务合同校验库。默认正式 API 未配置内核仍关闭；静态站点发布也不会开启开发桥接。

当前开发模式适合单人、零费用验证。多个本机 Vite 进程可以共享数据库和模拟任务状态，但不代表多人鉴权、跨机器服务或真实生成已完成。所需已验证图片已保留本机镜像（见 `verified-image-ingestion.md`），但尚无跨设备恢复入口；真实供应商入口必须替换开发身份，接入生产资产权限目录和持久化服务。
