# 超预留账单升级审批

阶段 3 第七里程碑。当前仅演练成本与审批逻辑，不发生真实供应商调用或扣费。

## 流程和权限

当 `billing_unknown` 任务的核实费用超过原预留时，普通核账接口仍拒绝结算。拥有 `run:reconcile-billing` 的人员可以提交升级申请；审批人必须拥有独立的 `run:approve-billing-overage` 权限，且不能与申请人是同一身份。即使成员同时拥有两种权限，也不能自批。

申请冻结以下内容：任务、动作编号、申请人和时间、原预留、币种、核实费用、当时批次上限、拟审批批次上限、扣费证据和原因。一个任务只能有一个待审批申请。

| 决定 | 任务 | 原预留 | 账本与批次上限 |
| --- | --- | --- | --- |
| 提交申请 | 计费待核对 | 保留 | 不结算，不调整上限 |
| 批准且检查通过 | 失败，等待人工决定后续 | 释放 | 按实际金额结算，更新明确批准的批次上限 |
| 拒绝 | 计费待核对 | 保留 | 保留原上限和申请证据 |
| 预算不足或快照失效 | 仍待审批、计费待核对 | 保留 | 不结算，不调整上限 |

以上决定都不会自动创建重试、派发任务或调整项目总预算。批准后任务仍没有可用的生成产物；如需继续产出，人工重试必须再次通过预算检查。

## 金额检查

使用整数最小货币单位，不以浮点金额记账。

- 核实费用必须大于原预留；否则走普通核账。
- 拟审批批次上限不能低于当时的批次上限。
- 它还必须覆盖：批次已结算费用 + 批次当前预留 + 本次核实费用 − 本任务原预留。不能遗漏同批次其他输出仍占用的预留。
- 审批时重新检查全部批次费用和当前项目可用预算；项目可用预算必须至少等于本次费用超出原预留的差额。
- 批次上限不能替代项目额度。即使批准较大的批次上限，也不会增加项目总预算或制造资金。
- 如果其他申请先被批准并改变批次上限，旧申请不能直接批准；可以拒绝旧申请并重新提交新快照。
- 拒绝不产生财务变更，因此即使当前批次上限已变化，仍可按原申请快照拒绝并留下意见。

费用已发生但项目预算无法覆盖时，申请保留核实费用和证据，系统保持冻结。当前不提供项目追加预算审批或真实账单争议处理，不会把费用改小或当作未扣费来消除告警。

## 幂等与不可覆盖

- 提交按任务和 `requestId` 幂等；相同身份和参数重放返回原申请，参数或身份漂移冲突。
- 审批按申请和 `reviewId` 幂等；同一审批人、决定和完整参数重放不会再次结算。
- 已批准或拒绝的记录不能被另一个动作覆盖；更正需保留旧记录并创建新申请。
- 被预算或快照检查阻止的审批不算完成，不消耗成功审批动作编号。释放其他预算后可以重新检查，但不能跳过财务闸门。
- 待审批时普通核账、取消和重试不能释放此任务预留。
- 请求与审批记录、账本和审计共同持久化。恢复时验证动作指纹、任务归属、申请/审批证据、不同人员、预留状态和结算金额。
- 旧版本聚合没有审批列表时迁移为 `[]`，不会清空已有任务或预算。

## API

`POST /v1/run-jobs/:jobId/billing-overages`

必需字段：`requestId`、`expectedReservedMinor`、`expectedCurrency`、`expectedBatchMaxCostMinor`、`actualCostMinor`、`requestedBatchMaxCostMinor`、`evidenceRef`、`reason`。

`POST /v1/run-jobs/:jobId/billing-overages/:overageId/review`

必需字段：`reviewId`、`decision`（`approve` / `reject`）、`expectedReservedMinor`、`expectedCurrency`、`expectedActualCostMinor`、`expectedBatchMaxCostMinor`、`expectedRequestedBatchMaxCostMinor`、`evidenceRef`、`note`。审批人不能在审批请求中换掉实际费用或上限，只能确认申请快照或拒绝。

两条路由返回完整批次聚合，新增 `billingOverages` 数组。合同拒绝额外字段、空证据/理由/意见及无效金额。默认未配置内核仍关闭，配置内核后也要求认证、租户边界和独立权限。

## 画布与开发身份

核账金额超过预留后，画布展示升级申请表；审批记录显示状态、费用、上限变动、申请证据与原因。审批表显示新增支出、原/新上限，并要求单独的审批证据和意见。

仅本地 Vite 桥接会在明确的审批路由中提供模拟 `local-reviewer` 身份；其他路由使用不含审批权限的 `local-designer`。审批人在此只是同一操作者的开发角色演练，不是真实第二个人或多人鉴权。正式 API 必须使用真实成员身份，不能复制该身份代入机制。

提交后响应不确定时，当前表单锁定参数并保留动作编号，重试原动作不会重复申请或入账。返回任务后可刷新查看服务端结果；已登记的申请和审批记录在刷新后恢复。

仍使用单进程原子 JSON 文件存储，不提供跨进程事务或并发财务提交保护。接入真实供应商前，必须完成数据库事务化、真实权限和权威资产校验。
